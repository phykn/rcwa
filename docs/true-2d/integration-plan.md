## Outcome and architecture

Support explicit project schema 1.2 through the existing validate → submit → bounded worker → poll/cancel → snapshot/import/reload lifecycle. Use one shared normalization/canonical-hash path, one JobManager, one HTTP API, and the existing thin MCP transport. Add version dispatch at boundaries; do not create a second job store, persistence table, solver service or alternate client workflow. Keep the existing 1D solver, historical contracts and saved-result readers intact.

The genuine 2D numerical adapter remains the sole 2D implementation. It supports centered axis-aligned rectangular inclusions/holes, homogeneous and x-invariant-y 1D layers, one common orthogonal x/y period pair, isotropic material tables, and the demonstrated outgoing local s/p powers. No phase/Jones, fitted 2D parameters, arbitrary polygons/offsets/rotations, measured-device claims or automatic convergence certification are added.

## Project dispatch and JSON Schema decisions

- Omitted `schema_version` retains historical 1.0 parsing and its one-rectangle scope. Explicit 1.0 and 1.1 retain their existing semantics. Only explicit string `"1.2"` selects 2D; reject null, numeric, unknown and unsupported versions without fallback, guessing or migration.
- Incoming HTTP and MCP use strict validation. Preserve the accepted first-use `InputProject` behavior: nested booleans/numeric strings do not become physical numbers. Integer JSON numbers are allowed for float-valued dimensions and normalize to the same floats. Historical normalized saved records retain the separate compatible reader; do not loosen new-request strictness to read history.
- Use one `parse_project`/normalization entry point with an explicit strict-request versus historical-read policy. It must copy/revalidate model instances as well as dicts; mutating an in-memory model must never bypass normalized input identity.
- 1.2 requires `geometry` on **all three** layer branches: `rectangle_2d`, `rectangle_1d`, `homogeneous`. Runtime already requires the discriminator; generated JSON Schema must add an equivalent required-tag constraint specifically inside the 1.2 layer union. Do not make legacy Layer/HomogeneousLayer constructor defaults globally required. Legacy omitted tags continue to mean rectangle_1d as before.
- Export project/forward-result unions that reflect actual version selection. Avoid discriminating the entire project union solely on a required version field because that would incorrectly reject legacy omitted versions. For results, nested result-type then result-schema-version selection must distinguish both forward variants from synthetic-fit results.
- Finalize the public 1.2 metadata marker/adapter version once, shared between producer, validator and capabilities. Existing `1.2.0-numerical` / `numerical_only` evidence remains historical; do not claim an old result was emitted by a promoted adapter.
- **Representational exception:** standard JSON Schema treats mathematically integral JSON numbers such as `3` and `3.0` alike, whereas strict Pydantic integer harmonics accept the integer token and reject a parsed float. Preserve legacy and 2D strict integer runtime handling; document this unavoidable schema/runtime difference in capabilities/tool descriptions and assert it explicitly in tests. Do not claim absolute parity or weaken harmonics strictness. Float-valued dimensions still accept integral numbers and normalize them consistently.
- Keep public 2D worker binding stricter than offline reference helpers: exact project basis, normal inverse-rule factorization, no offline override, complete (m,n) lattice, real input hash, requested wavelength/polarization set and exact physical layer counts. A 1.0/1.1 project still legitimately emits the current legacy 1.1 result; never require their input and result version strings to be identical.

## Canonicalization and provenance decisions

Use the existing canonical representation: normalized model JSON, sorted keys, compact separators, `ensure_ascii=False`, UTF-8, finite values only. Do not introduce Unicode normalization, transliteration, key-dropping or a browser-created alternate cryptographic canonical form. Pre-existing API 1.0/1.1 hashes must remain exact. Before changes, freeze representative legacy Unicode and signed-zero hashes from the final accepted first-use release itself. Preserve its existing signed-zero serialization; do not silently normalize numeric signs or Unicode sequences.

The shared core serializer has no database or API imports. Storage's `canonical_hash` retains its callable behavior for already normalized dicts. Boundary code obtains the normalized model/dict and hash together; solver_2d's helper revalidates its model before using that same serializer. The 1.2 result binder uses the identical function instead of copying serialization rules.

The server-owned immutable job input is the source of truth. The worker result's input hash, job hash and server snapshot provenance hash must agree. Derive snapshot adapter version from the validated result, not the existing global legacy engine-info constant. A changed geometry, azimuth, period, y width, material/table, polarization or wavelength input must change the normalized hash; equivalent key ordering and integer/float spelling must not. Human names/source strings are part of identity, including Korean and emoji.

Imports remain `unverified_import` even if they claim server provenance. Saving by succeeded forward job ID stays idempotent and never accepts caller-supplied input/result substitutions. Old 1.0 result readers and historical server provenance remain intact. Public JSON intake rejects lone surrogate keys/values before hashing/persistence, retaining the first-use release's size/Unicode protections.

## Resource profile and real-process acceptance

Conservatively classify every 1.2 project as one 2D job, even if all layers are uniform. Use at most one active 2D process and at most two total processes. One 2D + one legacy forward/fit may run if measured memory/runtime headroom passes; a second 2D gets the existing structured capacity response immediately, without allocating a process or retaining a phantom job. No queue or automatic retry is added.

Proposed unchanged public bounds: Hx/Hy each 1–5 (max 121 retained (m,n) orders), 1–31 wavelengths, 1–8 layers, each thickness 0–2000 nm, original material/table/angle/period ranges, one API process, 120 s hard worker deadline. Existing 2 MB request, 8 MB worker-output/transport/proposal limits remain hard bounds; keep the measured 6 MB result target as headroom, not a promised maximum response. Measure full snapshot and stdio MCP envelope bytes with maximum permitted material tables, not only raw result bytes or constant-material numerical fixtures; account for the actual SDK representation and request-cap-admissible table combinations. Capabilities retain legacy limit fields and add explicit version-specific profiles so no client mistakes 81 legacy wavelengths or 20 legacy harmonics for 2D limits.

The incoming/outgoing byte limits are asymmetric by design. The measured H5 result is approximately 2.24 MB, already above the 2 MB POST-body cap. A full exported result submitted to `/api/projects` above that cap must fail clearly with structured HTTP 413; do not raise the cap silently or imply every export is directly re-uploadable. Project-only import (`result: null`, within the cap) and server snapshot save by succeeded job ID remain available and tested. The later browser-local file viewer has a separate existing 20 MiB file limit; local viewing/export does not imply permission or capacity to POST/persist the same bytes. Test the real measured full-result file, just-under/over byte boundaries with multibyte Unicode, the usable project-only recovery, and ID-only server snapshot reload. Any future larger bounded import route is a separate reviewed change.

Define terminal races before implementation: a job has exactly one terminal transition. Use monotonic deadline checks immediately before committing an outcome; at/after the deadline, a not-yet-terminal job becomes timeout failure, even if its child has just completed but its result has not been accepted. Once accepted as succeeded/cancelled/failed, later output, cancellation or polling cannot revive or overwrite that state. Snapshot save can use only the single committed succeeded outcome. This conservative observation-time deadline policy may reject a just-completed result at the boundary; it avoids publishing an uncommitted result after the hard deadline and is explicitly tested.

Required process tests:

- Actual H5/31-wavelength/8-layer solves for high-contrast and extreme absorbing cases; measure spawned child peak RSS, wall time, result/envelope bytes and successful output binding. Include unequal-axis basis and both polarizations.
- Two independent clients racing 2D submissions: exactly one admitted. Admit two ordinary legacy jobs; reject a third. Admit one 2D + one legacy job, reject all further work until a slot is really released. Measure simultaneous worst bounded legacy-fit + 2D resource headroom, with one BLAS thread each.
- Cancel a real H5 child while it is alive; confirm termination/join/close, no child PID and no temporary output, then a fresh 2D job succeeds. Repeated cancellation and cancellation after completion are safe. No blanket process-name termination.
- Use an injectable short deadline for deterministic CI checks on a real child; assert timeout classification, kill fallback where necessary, output cleanup and successful subsequent admission. Retain one release-level watchdog test with the actual 120 s configuration and a deliberately blocked disposable worker; it verifies lifecycle handling, not physics performance.
- Failed start, nonzero child exit, missing/partial/oversized JSON, invalid envelope, nonfinite or wrong-schema result, and exceptions in validation: no success, no leaked slot/process/file; typed failure, followed by a successful fresh job. Do not leave a reserved 2D slot after `process.start()` failure.
- Complete just before, exactly at and just after the deadline; completion concurrent with cancel, poll and snapshot save; result validation crossing the deadline; repeated poll/cancel after terminal state. Assert one outcome/timestamp, no snapshot of cancelled/failed work, no orphan output and subsequent admission. Inject validation, join/close and unlink/cleanup exceptions; a single bad job must not kill the observer or strand a slot. Recoverable cleanup faults must be retried/cleared; persistent cleanup failure must be explicit rather than reported as successful cleanup.
- Shutdown during a live 2D run cleans the owned child and temporary directory. Restart forgets volatile jobs but reloads saved SQLite and PostgreSQL snapshots with unchanged provenance. Include 100-job history eviction and immutable request capture.

Implementation review adds a 64,000,000-byte estimated completed-history budget
alongside the 100-record limit. Cache recursive Python-object size per completed
job plus captured input, and evict oldest completed records deterministically.
Protect active/cleanup-owned records; cleanup-pending records block admission,
while unreaped children continue occupying their numerical slots. A single
oversized success fails `history_limit` before terminal commit. Persisted snapshots
are unaffected; an evicted volatile job is 404, and callers must save useful
results before eviction. Test count and byte boundaries, saved-result retention,
cleanup protection, exactly-once sizing, deadline crossing during sizing, and
bounded retention with copies of the actual maximum-table input/result.
